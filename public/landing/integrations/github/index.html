a github bot that reads the work before you weigh in

connect github to a bot in dusk bot and ask it to read issues, inspect pull request files or gather changes for a release. choose claude, chatgpt or another ai for the bot. start with a reader that reports in your chat; add specific write actions only when you want labels, assignments or comments changed.

by the dusk bot team · checked 12 november 2026 · how we made this

what a bot can do in GitHub

github work often starts with a question: is this report new, what changed, or who is waiting? these actions let a bot collect the evidence before suggesting a next step.

actiondusk bot treats it aswhat you would use it for
Search issues and pull requestsreadlook for earlier reports of the same error before calling a bug new
Get an issuereadread the reproduction steps and the original report
Get issue commentsreadcheck whether someone already found a workaround
List pull requests filesreadsee which files a proposed change touches
List reviews for a pull requestreadread reviewer feedback before summarising what is blocked
List commitsreadgather commit messages for a release briefing
Add labels to an issuechangeapply a triage label after you have agreed the rules
Create an issue commentsend: asks firstpost a requested follow-up through the sending approval setting

composio, the connection service dusk bot uses for apps, lists 905 GitHub actions (catalog version 20261104_00, read 12 november 20265). dusk bot treats 474 of them as reads, 13 as sends and the other 418 as changes. an action counts as a read only when its name starts with a read word like get, list or search, so a bot you allow only to read can never call the rest. a send is anything that reaches a person outside the app or moves money, like add email for auth user: it waits for your Allow unless you've given that bot a daily amount it may send alone.

connect GitHub

  1. open Connected apps in the sidebar.
  2. pick GitHub and sign in on GitHub's own page, so your password goes to them and never to a bot.
  3. choose which bots may use it, and whether each may only read or may also change things. your bookkeeper doesn't need your GitHub.
  4. ask in plain words. reading and drafting happen freely; sending asks you first.

open Connected apps, connect github and give access to the bot doing repository work. sign-in takes place on github's page. tell the bot the exact owner and repository, then choose read-only access for its first review. an action being in the catalog does not mean you have allowed that bot to use it.

routines to copy

try these as messages to a repository bot. each keeps the decision in your chat, so you can check the evidence before adding writes.

new report check

when a github issue opens in acme/widget, read it and search existing issues for the same error. tell me possible duplicates and which reproduction details are missing. do not label, assign, close or comment.

when a github issue opens · a triage note with issue references

review waiting room

every tuesday at 10, read open pull requests in acme/widget and their reviews. group them into waiting for author, waiting for reviewer and unclear. cite the review that supports each choice. leave everything unchanged.

tuesdays at 10:00 · a review queue grouped by the next person needed

release reading list

every thursday at 3, list commits in acme/widget since monday. draft a release outline in this chat, grouping fixes and additions. mark anything whose user impact is unclear. do not create a release or tag.

thursdays at 15:00 · an unpublished release outline

what it asks you first

posting an issue comment is a send: by default it brings up Allow or Deny. a daily sending amount can change that, and so can Full access for a bot with no sending rule of its own (up to 25 a day), so check the bot's sending setting before enabling comments.

labels, assignments, issue closure, merges and submitting a pull request review are other kinds of changes. do not assume they pause for a send card. keep the bot read-only for review work, or include "ask me before you change anything" in a routine that needs write access.

what it cannot do

  • merge, label or assign with a read-only github grant. the permission check stops a write before it reaches the app; reading a pull request is not permission to merge it.
  • keep triaging on a sleeping laptop. local event routines need dusk bot running and the computer awake. use dusk cloud if the repository needs attention while your machine is off.
  • prove a fix works just by reading an issue or diff. these routines collect repository evidence; they do not establish that you ran the code or reproduced the bug.

give it a repository boundary

name the repo in every routine, especially if your account can reach several. explain what your labels mean before allowing label changes. a report without reproduction steps should remain uncertain, rather than becoming a confident diagnosis. the issue triage routine is a useful next step.

keep discussion and tracking together

if the team plans in linear, let that tracker own priority. github can supply the issue and code context. a slack digest can cover discussion, but a suggestion in chat should not silently become a change to a release plan.

questions

can i connect claude to github without building my own bot?

yes. connect github in dusk bot and pick the ai for your bot. the connection and the ai choice are separate; switching the ai keeps that bot's chats and memory.

can it close issues without asking me?

do not rely on a sending prompt for issue closure. leave github read-only if you only want advice, or explicitly instruct the routine to ask before any change.

where does my issue triage bot run when my laptop is closed?

on your own computer it pauses during sleep or while dusk bot is closed. dusk cloud provides an always-on machine for routines.
